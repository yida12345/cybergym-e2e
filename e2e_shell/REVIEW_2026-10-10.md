# E2E 外壳代码审查（2026-10-10）

当前实现不能按“完整保留 ExploitGym 必须外层功能、真实批量运行可用”验收。模块覆盖较广，但入口、任务提交、崩溃恢复、采集与导出之间存在确定的行为缺陷，会造成启动失败、漏跑、结果误分类、轨迹缺失或任务池停滞。

官方 E2E 仓库工作树干净，提示词与单阶段裁判逻辑有复用依据；这只能证明官方文件没有被修改，不能证明外壳运行行为与官方等价。用户明确要求的独立验证、可选成功条件等属于有意改变的评测配置，应与实现错误分开判断。

## P1：批量运行前应修复

### R01 — CC runtime 准备脚本不能成功完成

位置：[prepare_cc_runtime.py:90](/data/cybergym-e2e/e2e_shell/prepare_cc_runtime.py:90)、[prepare_cc_runtime.py:161](/data/cybergym-e2e/e2e_shell/prepare_cc_runtime.py:161)。

`npm install ... --prefix TMP` 没有使用全局安装，生成 `TMP/node_modules/@anthropic-ai/claude-code`，代码却查找 `TMP/lib/node_modules/...`，因而抛出“安装目录未生成”。本机离线 npm 包复现：安装返回 0，实际目录存在，代码期望目录不存在。

即使修复目录，安装器写入的是 `manifest.claude_code.claude_code_version`，`verify()` 读取的却是 `manifest.claude_code.version`；已复现 `KeyError: 'version'`，且 `main()` 会调用该核验。

此外，容器运行前只执行 Node 兼容性检查，没有执行实际 `claude --version`；`CC_INSTALL_MODE=per-container` 虽被配置解析接受，runner 没有对应安装分支。仅把配置中的 `2.1.91` 写入结果不构成实际版本证据。

修复与验收：统一 npm 布局和 manifest schema，使用准备好的 Node 执行 npm，核验实际 CC 版本；实现承诺的安装模式或拒绝未实现模式。覆盖首次准备、重复准备、manifest 核验及容器内 CLI 启动。

### R02 — 默认 Squid 与 capture 的地址和启动顺序不一致

位置：[orchestrator.py:464](/data/cybergym-e2e/e2e_shell/orchestrator.py:464)、[orchestrator.py:539](/data/cybergym-e2e/e2e_shell/orchestrator.py:539)、[network.py:197](/data/cybergym-e2e/e2e_shell/shelllib/network.py:197)。

默认 `CAPTURE_BIND_HOST` 为空，network-up 给 Squid ACL 的地址是 `127.0.0.1`，proxy-up 实际绑定 services 网关地址。Agent 请求的是后者，白名单配置却是前者。`_start_squid()` 还先启动 Squid，再复制配置文件，没有 reload/reconfigure；不能据此认定新配置已经生效。

这是静态调用链确认，未启动真实 Squid。修复应统一实际网关地址，并在启动前挂载/写入配置或明确重载；真实验收需从 internal 容器验证经 Squid 到 capture 的完整链路。

### R03 — 手动 stop 的 repeat 被计为完成，续跑会跳过

位置：[supervisor.py:235](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:235)、[queue.py:454](/data/cybergym-e2e/e2e_shell/shelllib/queue.py:454)。

`_run_task_repeats()` 对所有返回结果都使用 `count_repeat=True`，包括停止产生的 `indeterminate`，甚至回执无效的情况。`finish_attempt()` 随即将 slot 置 `done`。新复现中，停止时的第一个 repeat 已变为 done，剩下一个 pending。

ExploitGym 在 `/data/exploitgym/scripts/local_full_image/orchestrator.py:781` 明确对 `stop_requested` 使用 `count_repeat=False`。当前 E2E 没有保留这一关键行为，直接违背“手动停止后原 config 继续，中断任务重试”的要求。

修复与验收：将人工停止原因保留到提交层；中断 attempt 留历史、slot 回 pending，不消耗逻辑 repeat。分别测试准备、静默 CC、验证期间停止，以及停止与最终提交同时发生。

### R04 — generation 没有独立目录，旧回执与旧产物可串入新执行

位置：[supervisor.py:245](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:245)、[results.py:369](/data/cybergym-e2e/e2e_shell/shelllib/results.py:369)、[runner_adapter.py:611](/data/cybergym-e2e/e2e_shell/shelllib/runner_adapter.py:611)。

目录只有任务和 `rNNN`，不含 generation；重试会复用旧 result、receipt、候选文件、会话目录和部分日志。`verify_receipt()` 没有接收或核验当前 attempt 身份，也不核验声明的产物 hash。复制本轮候选文件失败时，辅助函数没有删除或拒绝旧文件。

已复现 g1/g2 输出目录相同，g2 接受 g1 的回执，回执 attempt_id 与当前 attempt_id 明确不同。结果可能是跳过尚未执行的新一轮、用旧产物评分，或覆盖历史证据。

修复与验收：每个物理 attempt 使用 scope/repeat/generation 唯一目录；回执绑定当前 task/mode/repeat/generation/attempt_id、策略及必需文件 hash。测试旧成功回执残留、旧失败回执残留、候选文件复制失败和多次 stop/resume。

### R05 — 回执恢复把失败写成成功，阶段表也无法完整重建

位置：[queue.py:560](/data/cybergym-e2e/e2e_shell/shelllib/queue.py:560)、[supervisor.py:216](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:216)。

有效回执只表示结果提交完整，不能表示任务成功。当前恢复分支却硬编码 `outcome='success'`。已复现磁盘 `result.json` 为 failed，恢复后数据库 outcome 为 success；状态面板及依赖数据库的成功率因此错误。

result/receipt 落盘到 `store_stage_results()` 之间还有崩溃窗口。恢复只补 attempt/slot，不从结果重建 `stage_results`；09 读取该表重新分组时会缺少已经保存的阶段信息。

修复与验收：回执核验返回可信结果，按原分类函数恢复真实 outcome/error，并在事务中恢复阶段表与完成记录。覆盖 success、failed、indeterminate 等合法终态，以及文件已落盘但阶段表尚未提交的窗口。

### R06 — 阻塞 readline 使静默推理期间的停止、超时和监控失效

位置：[cc_runner.py:232](/data/cybergym-e2e/e2e_shell/shelllib/cc_runner.py:232)。

循环先调用阻塞 `stdout.readline()`，之后才检查退出、总超时、result idle 和 stop/watchdog。完整缓存代理等待期间恰好可能长期无输出，导致控制器无法按预算或手动停止及时中止。

已复现超时 0.05 秒、stop 始终为真，本地静默进程仍运行约 0.61 秒后正常返回，`stop_reason=null`。另一次复现中，已退出进程 stdout 有三行，只保存了第一行：`poll()!=None` 使程序在读完缓冲区前退出，末尾 result 事件也可能丢失。

修复与验收：日志读取与定时控制分离，使用读线程/队列或非阻塞轮询；进程退出后排空剩余输出。必须覆盖完全静默、部分行无换行、退出时大块尾部输出及 result 后静默场景。

### R07 — worker 异常被登记为 finished，supervisor 跳过异常回收

位置：[supervisor.py:154](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:154)、[supervisor.py:304](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:304)、[runner_adapter.py:123](/data/cybergym-e2e/e2e_shell/shelllib/runner_adapter.py:123)。

worker 的 finally 无条件写 `finished`。supervisor 发现该状态就移除子进程，绕过 `_recover_dead_worker()`。镜像获取在 `run_attempt()` 的 try 外，真实拉取异常是可到达的触发路径。

已复现抛出模拟拉取异常后 worker=finished、task=running、attempt=running。其他 worker 可能一直 WAIT，或控制器带未完成任务退出；不会按承诺自动恢复和补拉。

修复与验收：区分正常结束与异常退出，结合 exitcode、活动 task/attempt 决定是否回收。回收还应先确认并终止旧执行进程、回收旧容器，再释放 slot，避免数据库已回 pending 而旧执行仍继续。

### R08 — 实际 capture 目录被离线聚合忽略，自动 drain 也指向错误目录

位置：[orchestrator.py:48](/data/cybergym-e2e/e2e_shell/orchestrator.py:48)、[orchestrator.py:542](/data/cybergym-e2e/e2e_shell/orchestrator.py:542)、[trajectory_adapter.py:68](/data/cybergym-e2e/e2e_shell/shelllib/trajectory_adapter.py:68)、[supervisor.py:420](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:420)。

真实名称是 `capture_logs/launch-时间-随机值`，聚合仅扫描 `launch_*`。已复现实际目录内有一条 capture，聚合却得到 launches=0、captures=0。原有测试使用下划线命名，掩盖了生产入口不一致。

自动收尾还构造 `launch_{launch_id}`；supervisor launch_id 与 proxy launch_id 独立生成，进一步偏离实际 capture_dir，可能直接跳过实际尚未完成的采集等待。

修复与验收：以数据库/服务记录中的实际目录作为统一来源，避免各处重新拼接；用生产 `_launch_id()` 生成目录进行聚合与 drain 集成测试。

### R09 — 在线导出没有实现轨迹关联/ShareGPT，更新还保留旧结果

位置：[online_export.py:162](/data/cybergym-e2e/e2e_shell/shelllib/online_export.py:162)、[online_export.py:203](/data/cybergym-e2e/e2e_shell/shelllib/online_export.py:203)、[util.py:205](/data/cybergym-e2e/e2e_shell/shelllib/util.py:205)。

发布记录只有 attempt_id、signature、checks、result、provisional，没有读取 capture 进行 message.id 关联，也没有调用轨迹 finalizer 或 ShareGPT exporter。复现确认没有 ShareGPT 目录。ExploitGym 的 `postprocess_online/pipeline.py` 包含关联、转换和 ShareGPT 物化，这些不能以元数据文件替代。

冻结缓存还按 attempt_id 固定路径，`hardlink_or_copy()` 发现目标存在就返回。已复现成功结果更新成失败后，报告 updates=1，公开视图仍为 success=1、failed=0。签名也未包含 capture/session 的变化，无法处理迟到采集数据。

`ONLINE_EXPORT_ENABLED`、`ONLINE_WORKERS` 被解析，但前者没有接入启动调度，后者没有实际并行导出消费点。原子发布还有先 unlink current 再 replace 的空窗，根链接逐个切换，异常时 pending 在 finally 中删除；这些也不构成完整的中断恢复保证。

修复与验收：补齐真实在线轨迹流水线，缓存按输入内容版本化，跟踪迟到 capture/session、更新与撤回；自动开关和并发参数接入真实入口。覆盖运行期间导出、迟到 capture、重新分类、发布任一步骤失败及一致读取。

### R10 — 活动/完成判断太晚，resume 会先改动队列

位置：[run_all.sh:42](/data/cybergym-e2e/e2e_shell/run_all.sh:42)、[02_prepare_dataset.sh:14](/data/cybergym-e2e/e2e_shell/02_prepare_dataset.sh:14)、[orchestrator.py:85](/data/cybergym-e2e/e2e_shell/orchestrator.py:85)、[orchestrator.py:129](/data/cybergym-e2e/e2e_shell/orchestrator.py:129)。

`run_all` 先 preflight、prepare/resume、网络、proxy、smoke，最后 launch 才检查 ACTIVE/COMPLETE。prepare 调用的 resume 没有启动锁或活跃 supervisor 检查，会直接恢复/重置活动 attempt、task 和 worker。直接执行 02/resume 可在 supervisor 仍运行时破坏其队列状态。

默认 preflight 还把本 scope 的正常端口占用一律判失败；若完成后服务仍在，重跑不会直接显示 COMPLETE。若服务已回收，完成实验又可能先重建服务并发出 smoke 请求，之后才发现 COMPLETE。proxy-up 每次生成新 launch_id，也使正常已有代理无法通过“同 run”目录核对。

launch.lock 仅保护 launch 子命令，Popen 返回后即释放，而 supervisor PID 由子进程稍后写入；两次相邻启动存在判活窗口。

修复与验收：把整个入口置于同一 scope 锁和状态机；先判活/完成，再做任何队列恢复、服务变更或模型请求；恢复前核对并收束旧执行者。覆盖直接重复 run_all、直接 02/resume、并发启动和 COMPLETE 零请求返回。

### R11 — Docker 超时恢复没有严格核对镜像、资源与挂载

### R12 — 离线后处理失败返回成功，ShareGPT 报告没有正确落盘

位置：[postprocess.py:99](/data/cybergym-e2e/e2e_shell/shelllib/postprocess.py:99)、[postprocess.py:134](/data/cybergym-e2e/e2e_shell/shelllib/postprocess.py:134)、[supervisor.py:427](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:427)。

finalizer/完整性分析非零退出被放入报告 error 字段，函数仍正常返回，CLI 返回 0，自动收尾随后把 export_status 写 done。已复现 finalizer exit=7，整个 finalize 正常返回。

共享 ShareGPT exporter 将总报告打印到 stdout；E2E 虽捕获 stdout，却没有保存，而后查找自身从未写入的 `successful_export_report.json` 等文件，成功执行也可能被记为 `error: exit=0`。ExploitGym 离线脚本会把 stdout 重定向到该文件并检查 JSON。

`exportable_trajectories` 目前只是有 session 的 attempt 数，不是成功关联并导出的轨迹数。修复应传递明确导出失败状态、保存/校验 exporter stdout，并分别报告 session 覆盖率、关联数、可用轨迹与 ShareGPT 样本数。

### R13 — 工作区准备把官方必需步骤失败改成忽略

位置：[workspace.py:125](/data/cybergym-e2e/e2e_shell/shelllib/workspace.py:125)、[workspace.py:148](/data/cybergym-e2e/e2e_shell/shelllib/workspace.py:148)。

官方 utils.py 对镜像残留清理、创建目录、安装 sudo/git 使用 `check=True`。外壳对首个清理命令和 apt 使用 `required=False`，其他清理命令不检查返回码，还设置 `arvo_residue_cleaned=True`。失败后可能继续使用有残留内容或依赖不足的工作区，改变基线语义。

这不是用户要求的阶段独立执行扩展。修复应保持官方必需步骤失败即中止，并归为准备/基础设施错误；若确实允许某项失败，需要明确适用条件与证据，不能无条件忽略。补充每个准备步骤非零退出的测试。

### R14 — 冻结与续跑核验不能保证实际执行输入未变

位置：[manifest.py:303](/data/cybergym-e2e/e2e_shell/shelllib/manifest.py:303)、[workspace.py:149](/data/cybergym-e2e/e2e_shell/shelllib/workspace.py:149)、[config.py:290](/data/cybergym-e2e/e2e_shell/shelllib/config.py:290)。

项目脚本虽被复制到 frozen，却没有逐个保存/核验 hash；资产核验主要覆盖 src.tgz、poc.bin、crash.log。capture 工具 hash 虽写 manifest，resume 没有比较，也继续执行共享目录中的实时文件。validate.py/deps 仍从实时 repo 复制，不是 manifest 对应的冻结副本。

核心指纹未覆盖阶段验证预算等影响可比性的配置。已复现修改冻结 compile.sh、capture 入口代码和 stage_validation_timeout_seconds 后，resume 核验仍返回 verified=true。

修复应核验并实际使用同一套冻结脚本/工具、固定依赖与 runtime 指纹；明确哪些参数允许续跑变更、哪些必须开新实验。避免“记录过 hash”被误当成“实际核验过 hash”。

### R15 — 资源预算与写层监控的统计口径不正确

位置：[01_preflight.sh:95](/data/cybergym-e2e/e2e_shell/01_preflight.sh:95)、[supervisor.py:91](/data/cybergym-e2e/e2e_shell/shelllib/supervisor.py:91)。

preflight 读出了现有容器 CPU/内存配额，却只打印，没有从可用预算扣减；和 ExploitGym 并跑时可能把已分配资源再次当成可用。应明确按配额预算或实际可用资源制定策略，纳入现有运行负载。

标为 attempt 级的 Watchdog 却累加整个 scope 所有容器写层，与单 attempt 上限比较。例如两个任务各写 9 GiB，单任务上限 16 GiB，当前范围会按 18 GiB 判超限。应按 attempt labels 统计，scope 总限额另设参数。此外 `512m` 的内存字符串在当前 preflight 解析分支会触发 float 转换错误。

### R16 — 连通性/反向测试不足以支持 effort 与隔离验收

位置：[cc_runner.py:297](/data/cybergym-e2e/e2e_shell/shelllib/cc_runner.py:297)、[orchestrator.py:674](/data/cybergym-e2e/e2e_shell/orchestrator.py:674)、[orchestrator.py:739](/data/cybergym-e2e/e2e_shell/orchestrator.py:739)。

真实 capture 请求 JSON 使用 `body_json`，effort 检查却读取 `body`；含 thinking 字段的真实格式样本已复现为 supported=false。smoke 使用手工 HTTP 请求，既不启动 CC，也不发送 effort 字段，因此不能证明 CC 2.1.91/high 的实际请求行为。

反向测试先把 ubuntu 容器放到 internal 网络，再尝试 apt 安装 curl；在没有预置 curl 且禁止外联时不能完成准备。允许路径判定只要求 curl 返回 0 且 HTTP code 不含 000，HTTP 403 等拒绝响应也会被接受；其他格式化字符串还存在 `%{{http_code}}` 不一致。

修复应预装探测工具或先在安装网络准备，再切换到 internal；明确要求健康端点 HTTP 200 与对应身份。effort 应通过实际 CC 辅助请求、正确 capture schema 和期望字段/值验证，区分“请求携带参数”和“上游已接受/执行参数”。

### R17 — 镜像自动回收未接入，手动回收映射也错误

位置：[orchestrator.py:365](/data/cybergym-e2e/e2e_shell/orchestrator.py:365)、[image_manager.py:206](/data/cybergym-e2e/e2e_shell/shelllib/image_manager.py:206)。

`IMAGE_CLEANUP_ENABLED=true` 只传给 manager，没有在正常任务完成路径调用 cleanup_owned_images；当前调用位于显式 cleanup/stop 的可选分支。ExploitGym 则在任务结束后调用镜像清理。

手动分支遍历 `counts['tasks']`，得到的是状态→计数，而非 task_path→状态，再比较计数是否等于字符串 done，导致消费者完成映射无效，镜像通常被判为 consumers_running 而无法清理。对于大量镜像，这会使磁盘持续累积。

修复应从 task 行构建映射，在全部共享消费者完成且无活动 lease 后自动回收本 scope 拥有的镜像。lease 的读改写还缺少互斥保护，需要覆盖同镜像多进程 acquire/release/cleanup 竞争，保留预先存在和外部引用的镜像。

### R18 — 不同 E2E 实验的 Agent/验证容器可能同名

位置：[queue.py:351](/data/cybergym-e2e/e2e_shell/shelllib/queue.py:351)、[runner_adapter.py:130](/data/cybergym-e2e/e2e_shell/shelllib/runner_adapter.py:130)、[runner_adapter.py:348](/data/cybergym-e2e/e2e_shell/shelllib/runner_adapter.py:348)。

attempt_id 的 hash 只包含 task 数据库 ID、mode、repeat、generation，没有 EXP/scope/task_path。容器名仅拼该 ID。两个新 E2E 实验很容易产生相同 task=1、r1、g1，从而在全局 Docker 命名空间冲突。

默认 cg-e2e 前缀没有与当前 ExploitGym 固定网络/容器名重合；这不意味着多 E2E 实验间也完全隔离。应加入稳定 scope 短 hash，并保证长度截断后仍包含完整唯一部分；测试两个不同 EXP 的同编号任务同时运行。

## 官方 E2E 行为保留情况

有依据保留的部分：

- 官方仓库没有工作树修改。
- `prompts.py` 从官方 `run_agent.py` AST 提取提示函数并核对函数 hash，没有重新撰写任务提示。
- `validation_entry.py` 调用官方 `validate.validate_task()`，通过 only_stage 选择阶段；prepare 在容器准备时执行，验证入口使用 run_prepare=False。
- 代码对每个启用的验证阶段创建新容器，准备工作区后执行验证；正常路径留存四阶段状态及其证据路径。
- 官方代码与外壳配置均指向 CC 2.1.91；实际安装与执行版本仍需 R01 修复后的实测。

经用户明确授权的差异：

- 官方前置阶段失败可能跳过后续阶段；外壳要求所有启用阶段独立执行。
- 外壳允许选择启用阶段和 success 条件，并保留各阶段结果用于重分组。这形成可配置评测 profile，不能把任意 profile 的成功率直接当成官方默认口径。
- 外壳加入任务池、重复次数、续跑、代理采集、资源约束与导出；这些不需要改写官方单阶段判断标准。
- 外壳采用独立 repeat，没有官方多次尝试的反馈/轨迹摘要循环；默认官方 max_attempts=1 的单次行为是比较对象。

不应视为已授权语义变化的部分：准备步骤失败仍继续、恢复把失败变成功、旧产物跨 generation 使用，以及日志/采集被丢弃。这些需要修复，不能以“外层封装”解释。

## 修复及验收顺序

1. 先修 R01/R02，准备工具和服务链路，否则真实任务入口无法可靠运行。
2. 修 R03–R07/R10，建立严格的状态机、独立 attempt 历史、准确恢复和可中止执行。没有这一层，扩大任务量会放大漏跑与误计分。

5. 单任务验收应覆盖正常运行、不同阶段失败、静默停止后同 EXP 接续、提交窗口崩溃恢复、离线/在线导出一致性及 COMPLETE 无额外请求。
